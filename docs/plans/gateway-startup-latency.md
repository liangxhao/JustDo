# Gateway 启动耗时待优化

记录日期：2026-10-25–26。用户反馈正常启动时 Gateway 超过一分钟，本轮先保留问题与测量依据，尚未确定根因或完成提速。

## 本次观测

依据用户提供的本地 `run_log.log`（开发启动，2026-10-25 21:13–21:15），只记录阶段名与耗时，不提交原始日志、凭据或会话正文。

| 观测边界 | 耗时 |
| --- | --- |
| Main 发起 startGateway 到标记 Gateway running | 67.327 秒 |
| Main 等待健康响应 | 66.940 秒 |
| 原生进程起点到完整 ready | 约 74.1 秒 |
| ready 后 startup maintenance | 19.568 秒 |
| ready 后 subagent recovery | 27.270 秒 |

健康响应、原生完整 ready、应用执行准入和首页揭幕是不同边界，不能互相代替。
后两项在 ready 后运行，不能加到上面的进程启动耗时，也不能推断整个界面阻塞了相同时长。

当前可见的主要阶段为 `process.bootstrap` 29.703 秒（其中环境选择 11.907 秒）、
`config.auth` 21.977 秒、`sidecars.main-session-recovery` 6.117 秒和
`sidecars.model-runtime` 6.480 秒。这些阶段包含嵌套或并行工作，不能直接相加；
`config.auth` 的聚合名称不能证明全部耗时来自认证或网络。

侧栏首次应用目录还需连接和准备精确的工作区会话；该日志中的 `mcp.app.discover`
响应约 731ms，无法据此将“正在加载应用列表”的全部等待归因于 draw.io 本身。

## 打开历史对话时的准备窗口

同日 23:47–23:50 更新日志中，Main 从 startGateway 到 running 为 98.944 秒；原生
`process.bootstrap` 53.049 秒、`config.auth` 22.178 秒，HTTP 绑定约在进程起点后
84.113 秒，全局 ready 约在 101.277 秒。ready 后启动维护仍运行 30.814 秒，
subagent recovery 运行 70.562 秒；这些边界不能合并为同一项“已可读取历史”。

该轮出现 7 条 `loadHistory FAILED`，错误为原生目标 Agent 会话库尚未完成后台准备。
全局 ready 后仍有明确 pending；4 条后台恢复日志没有打印 Agent 归属，不能据此
单独证明 main 或当前目标已可读取。目标历史真正成功返回才是该读取的完成证据。
同时有较高事件循环利用率、CPU 和长延迟警告，只能作为后续定位线索，不能仅凭它们
确定是会话数据量、插件、文件系统或后台恢复中的哪一项导致耗时。

本轮修复 Renderer 把原生准备误报为历史读取失败、且没有等待目标恢复的问题；
不绕过原生完整性或 writable admission，也不将此项视为原生准备提速。
Main 的弱健康探测与目标会话准入还须分开衡量：健康响应、全局 ready 和实际历史读取
各有不同语义，不能以 `/health`、任意非服务端错误响应或其它 Agent 的就绪代替目标准入。

## 模型变更后的重启中断

同日 22:34–22:41 的 `run_log.log` 记录默认模型配置先进入原生热更新。原生约 36 秒后完成
应用，宿主却已因 30 秒观察窗口不足请求重启，随后触发 `SIGUSR2` 原地重启。
Main 的另一处启动等待在 60.019 秒后判为未就绪，停止仍在重启的进程，再进行冷启动。
随后的 draining、连接不可用和恢复失败记录发生在这次宿主停止之后；新进程最终完成
ready，认证连接中的会话列表与配置读取恢复成功。这说明该轮连接中断包含宿主过早
替换进程的放大因素，不能据此判定模型服务或 Gateway 永久故障。

宿主修复共用原有配置重载的观察预算，超时保留仍存活的原生 owner，退出时立即取消
等待；详见[引擎启动与重启状态](../architecture/05-agent-engine.md#3-启动与重启状态)。
后续模型切换修复改用模型字段专用热更新，取消这条重启兜底，并将默认偏好确认移出
发送的配置队列；首发明确绑定用户选择，不等待全局默认值。会话模型绑定与执行权限
仍由原生确认，参见 [Cowork 生命周期](../architecture/04-cowork-system.md#4-后续回合与设置修改)。
此项消除重复冷启动的错误处理，不证明 Gateway 的单次启动速度已改善。该轮后继
冷启动的 HTTP listener 约 70.1 秒才绑定，仍需按下面的工作拆分测量。

## 首次发送遇到的准备窗口

2026-10-26 更新日志还记录了首页切换模型后首次创建会话失败：全局 ready 之后，
`sessions.create` 返回 `SessionMutationFactsUnavailableError` / `UNAVAILABLE`，未提供
结构化准备码或可重试标记。该轮 Main 标记 running 耗时约 65 秒，原生 bootstrap
约 20 秒；目标 create 失败耗时约 3.57 秒。失败前约 25 毫秒出现一次无 Agent 标识的
后台库恢复记录，不能据此断定该目标已就绪或定位到具体创建阶段。

应用改为发送后的目标只读准备等待，再执行唯一一次 create；不按这个错误自动重试创建，
也不绕过原生访问事实。此项处理准备窗口中的首发体验，仍不代表原生启动或存储恢复提速。

## 后续工作

- 使用同一机器、相同配置及冻结原生产物，对安装版冷启动和再次启动分别测量，标明缓存与网络条件。
- 将环境选择、配置/插件准备、会话恢复和模型运行时初始化分段定位，区分本地计算、磁盘、进程启动与内部服务等待。
- 分别记录进程创建、健康响应、原生 ready、执行准入、首页揭幕与侧栏目录可用的时间；检查 ready 后维护是否与首页工作区准备争用资源。
- 优先通过宿主或扩展的公开接口减少重复工作；原生修改须遵循运行时补丁与独立交叉评审规则。
- 优化不得绕过会话身份、权限、真实 ready 或安全清理；不能以缩短超时、提前标成功或隐藏进度作为性能改善。

这些记录尚不能证明问题无法优化。启动窗口过渡和侧栏等待动画属于体验修复，不作为 Gateway 提速验收。
