# 应用插件开发指南

本指南面向使用 App Plugin SDK 编写应用插件，或定制 Agent Team / Swarm Workflow 的开发者。目标是让业务代码、界面、配置和历史入口随插件一起交付，应用宿主只组合公共能力。

这里的“应用插件”是一个原生 Extension 包，加上可选的 Main / Browser 应用部分；后者通过 `app.plugin.json` 和 `@app-plugin/sdk` 接入。本文描述当前仓库的 SDK v1，实际版本以 [SDK package.json](../../../../plugins/sdk/app-plugin-sdk/package.json)、[SDK 契约](../../../../plugins/sdk/app-plugin-sdk/contracts.ts)和[应用插件宿主架构](../app-plugin-runtime.md)为准。

## 先选择合适的扩展形式

| 需求                                                  | 优先使用的形式                             |
| ----------------------------------------------------- | ------------------------------------------ |
| 给助手增加操作说明、工作方法或资源文件                | Skill；元数据和发现由 Gateway 技能接口负责 |
| 接入外部工具服务器                                    | MCP；遵循已有配置和认证流程                |
| 注册原生工具、Gateway 方法、执行 hook、渠道或原生服务 | OpenClaw Extension                         |
| 同时提供应用界面、产品会话协调、设置或历史入口        | 本指南的 Native + Main + Browser 应用插件  |
| 创建 SDK 尚未提供的窗口类型、系统能力或全新宿主流程   | 先设计公共 SDK / 宿主能力，再让插件消费它  |

不要求每个原生 Extension 都新增 Main / Browser。当前应用插件构建器要求应用清单同时声明这两个入口；没有 Main 业务时可返回空命令列表，没有 UI 时可以不注册视图。

## 插件可以改到什么程度

在 SDK 已有能力内，可以只修改插件的工具和调度逻辑、产品协调器、数据规则、React 界面、输入模式、双语文案、设置及历史入口，再独立构建和安装完整插件包。通常不需要修改应用 `src` 或重新编译应用。

这不代表任意宿主行为都能被重写。窗口壳、preload 权限边界、普通聊天控制器、Gateway 连接和消息权威仍由各自宿主持有。公共 SDK 没有暴露的能力，需要增加通用接口，不能从插件绕回导入应用内部实现。

当前执行可信 Main 进程内代码和同页面 Browser 代码。代码审核、产物校验、原生授权与生命周期检查都有作用，但不是低信任插件沙箱。不要把“声明了 capability”理解成操作系统级隔离。

## 两条开发路线

**新建独立插件：** 从本目录的 [Hello Panel 源码](examples/hello-panel)开始，用仓库构建器产生完整可安装目录。这个示例没有 Team / Workflow 的相邻源码依赖。

**定制现有插件：** 保留同一个插件 ID，修改自己的副本，声明并安装实际依赖，构建后通过已开放的扩展管理流程替换。自定义安装版本会遮蔽同 ID 的捆绑版本，新产物须在受管安装中重新校验并登记确切 hash 的信任；安装或替换代码时宿主重启后台 Gateway，软件保持打开。已安装插件的普通启用、关闭热生效，不重启 Gateway。更换 ID 则属于另一个插件，还要同步修改原生方法、配置和数据所有权，不能只改文件夹名称。

## 现行说明与剩余验收

本目录负责作者操作步骤；长期所有权和协议以[架构说明](../app-plugin-runtime.md)为准，用户行为以[功能索引](../../../features/README.md)为准。安装、卸载入口是否开放仍由产品策略决定，本文不表示当前所有发行包都允许导入外部插件。正式安装包、真实模型、跨平台和低信任隔离等剩余范围见架构说明的“尚未完成的生产验证”；不能把 smoke probe 通过当成全部生产场景已验收。
