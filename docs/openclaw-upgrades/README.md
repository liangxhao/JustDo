# OpenClaw 升级记录

本目录按目标版本保存差异、产品接入决策、审查和当时的验证范围。记录只适用于对应版本与提交，不替代当前架构，也不是最新补丁清单。

- [v2026.10.6 升级记录](v2026.10.6/README.md)：目标发布包、独立 Node 运行时、33 项补丁与 SDK/插件适配及验证边界。
- [v2026.10.4 升级记录](v2026.10.4/README.md)：目标包、补丁与 SDK 适配，以及已验证和待人工验收的范围。
- [v2026.9.8 升级与验收索引](v2026.9.8/README.md)：主要升级决策、关键修复与合并后的验收摘要。
- [v2026.9.6 历史升级审计](v2026.9.6/README.md)：从 9.2 升级的历史记录；该应用构建未发布。

当前版本以 `package.json.openclaw.version` 为准；操作规范见[补丁指南](../openclaw-runtime-patches.md)，能力、原生处置及移除条件以[当前补丁总账](../../scripts/patches/v2026.10.6/README.md)为准。

## 目录结构要求

每个目标版本使用独立的 `vYYYY.M.D/` 目录。后续升级统一保存以下四个文件；其中 `module-api-audit.md` 是必交的逐模块上游接口专项报告，不能用编译通过或测试总数代替。其他专项内容继续使用文件内章节，不另起主题文件或重复使用版本号命名。

```text
openclaw-upgrades/
  README.md
  vYYYY.M.D/
    README.md
    upgrade.md
    validation.md
    module-api-audit.md
```

| 文件 | 必须记录的内容 | 内容边界 |
| --- | --- | --- |
| `README.md` | 本版本范围、历史适用边界，以及另外三个文件的入口 | 保持简短，不堆放升级正文与测试流水 |
| `upgrade.md` | 来源与目标版本、源码/发布包依据、上游变化、产品接入与不接入的决策、补丁和 SDK/依赖适配 | 解释改了什么、为什么改；验证结果链接到 `validation.md` |
| `validation.md` | 自动化测试、构建与产物身份、独立复审、真实界面/设备/安装版验收、失败及修复复验、未完成项和复验入口 | 按阶段或专题分节，明确提交、日期、环境与证据边界；没有证据的项目写明未记录或未验收 |
| `module-api-audit.md` | 每个功能模块的旧/新原生 API、事件、SDK、配置与资源协议差异，生产调用方、是否需要适配、测试用例、证据与剩余限制 | 必须覆盖功能索引和实际调用清单；无需修改也要给出源码对照与回归依据；模拟测试、原生契约与真实服务验收分别记录 |

新增报告从 v2026.10.6 起执行，具体要求和逐模块勾选项见[模块接口审计清单](../upgrade-checklist/module-api-audit.md)，本轮见 [v2026.10.6 专项报告](v2026.10.6/module-api-audit.md)。历史版本保留当时实际记录，不补造缺失的测试或验收结论；不同阶段的结果不可累加或冒充最终产物证明。运行和产物验证仍统一加入 `validation.md` 的具名章节，接口报告引用对应证据。

每轮存储审计还必须记录四类启动、跨版本升级的来源数据范围和降级策略。
降级先提醒并提供“仍然启动”，确认后继续正常检查；实际数据兼容性和加载错误不得跳过。
正常升级、迁移升级与降级不能以同一“安装成功”结论替代。

移动内容时同步修正仓库内引用、相对路径与章节锚点。当前契约仍维护在 `docs/architecture/`、`docs/features/`，逐项补丁清单在 `scripts/patches/<version>/`，下载信息在 `docs/offline-downloads.md`；这里保存升级历史，不提交原始日志或凭据。
